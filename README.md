# agent-memory-demo · 带遗忘、强化、冲突消解与可观测性的 Agent 长期记忆层

[![tests](https://github.com/cao290/agent-memory-demo/actions/workflows/tests.yml/badge.svg)](https://github.com/cao290/agent-memory-demo/actions/workflows/tests.yml)
![python](https://img.shields.io/badge/python-3.10%2B-blue)
![license](https://img.shields.io/badge/license-MIT-green)

> 一个最小可用的 Agent 长期记忆系统。**零重依赖**——默认只用 `numpy` + `jieba` + 标准库
> (SQLite)，任何机器 clone 下来离线即可复现全部数字。含自绘可观测性面板，
> 以及一个**可选**语义嵌入后端（ONNX，凭 onnxruntime 即可，无需 PyTorch，失败自动降级）。

---

## 这个项目想解决什么问题

普通 RAG 的隐含假设是「所有文档块永远有效、权重相等」。放到真实的长期 Agent 里，
这个假设会崩：

- 库越堆越大，检索噪声越来越高；
- 三个月前的**过时结论**和昨天刚校准的结论，被一视同仁地召回；
- 新旧两条冲突记忆同时被取回，模型对着两份矛盾信息瞎猜；
- 上下文无限膨胀，token 成本失控。

一句话：**没有遗忘机制的记忆系统，比没有记忆更糟糕。**

本项目给每条记忆加上**生命周期**，让记忆「用进废退」：

```
strength(t) = 衰减(时间) × 强化(使用)
```

- **衰减**：艾宾浩斯式遗忘曲线 `exp(-Δt/τ)`，久不用则自然淡出；
- **强化**：被召回一次就「复习」一次，抬高记忆稳定度；遵循**间距效应**（间隔越久再复习，增益越大）；
- **融合**：检索排序 = 相关度 × 强度，过时记忆自动沉底；强度跌破阈值进入待淘汰区。

### 实测结果（本机 · 318 条记忆 · k=5）

#### 实验一 · 召回率（三种通道）

| 通道 | 说明 | Recall@5 |
|---|---|---|
| plain | 朴素 RAG：只按词相关度 | 0.4242 |
| hybrid | 词+字混合相关度，无强度 | **0.4576** |
| memory | 完整记忆层：相关度 × 强度 | 0.3576 |

#### 实验一b · 强度权重扫描（真正的取舍曲线）

```
w=0.0 : 0.4576   ← 等价纯 RAG，raw recall 最高
w=0.1 : 0.4576
w=0.2 : 0.3576
w=0.35: 0.3576   ← 默认
...
```

**结论：强度权重是按任务调的旋钮，不是越大越好。** 详见「三个设计取舍」。

#### 实验二 · 新旧竞争（记忆层独能力）

同主题放旧版 / 新版两条记忆，纯 RAG 的 top-1 命中新版仅 **0.667**，记忆层 **1.0000**。

### 冲突消解实测（本机 · 318 条真实记忆）

| 指标 | 结果 |
|---|---|
| 冲突污染率（消解前，新旧矛盾记忆同时被召回的比例） | **100%** |
| 冲突污染率（消解后） | **0%** |
| 真实库自动取代对数（误伤） | **0** |
| 真实库待裁决对数 | 378 |

**消解把「矛盾记忆同时被召回」的比例从 100% 降到 0%，同时在真实库上误伤为 0。**
这两条要放在一起看：只降污染不看误伤，就等于用「大量删记忆」换指标好看。详见下文。

## 冲突消解 —— 这个项目技术深度最高的一块

### 为什么需要它

只做「写入 + 检索 + 遗忘」，库里的记忆会互相矛盾而系统毫无察觉：

- 你三个月前记下「用像素法判断水印」，昨天校准出「像素法是错的」；
- 两条都会被召回，模型同时拿到两个矛盾结论，只能瞎猜；
- 更糟的是旧的那条可能因为被引用得多、强度更高，**排在前面**。

遗忘衰减能缓解，但它是**时间驱动**的，对付不了「新记忆刚写入、旧记忆还很新鲜」的即时冲突。

### 做三件事

1. **检测**：判断两条记忆是不是在说同一件事（复合相似度超阈值）。
2. **判向**：谁取代谁？—— **晚写入的优先**（新知识覆盖旧知识），同源文档的更新同理。
3. **消解**：旧的标记 `superseded` 并链接到新的，检索默认不再返回旧的。

### 关键设计：误判比漏判危险

消解会**隐藏**一条记忆。如果判错了，就是静默丢掉一条可能正确的记忆——比不消解更糟。
所以策略刻意保守，分两档：

| 情形 | 处理 |
|---|---|
| 相似度极高 **且** 明确时间先后 | 自动 `supersede` |
| 相似度够高但证据不足 | 只记 `contradicts`，**交上游（人/LLM）裁决，不自动删** |

实测印证了这个保守性：真实 318 条库上，**自动取代 0 对，待裁决 378 对**。
因为同源文档的不同片段共享标题、时间戳相同，不构成「版本更新」，不该被自动取代。
而在构造的「旧→新」冲突上，消解把污染率从 **100% 降到 0%**。

### 消解不是删除，是可追溯

旧的记忆不会消失，只是 `state → superseded`，并写一条 `memory_links`：

```
#2 --supersedes--> #1  (score=0.49)
    同源文档内的更新（晚 30.0 天）→ 新版本覆盖旧版本
```

顺着关系图能从任何一条被取代的记忆找到取代它的新记忆，**出问题能回滚**。

## 可观测性面板 —— 让静默故障可见

记忆系统最危险的地方是**静默出错**：记忆被错误取代了、该召回的被遗忘了、强度曲线跑偏了——
这些在日志里不报错，只会在几周后表现为「Agent 变笨了」。可观测性把内部状态摊开，让故障可见。

`python dashboard_demo.py` 生成 `data/dashboard.html`，含四张图（纯 SVG 自绘，零前端依赖）：

| 图 | 看什么 |
|---|---|
| ① 生命周期概览 | active / superseded / 待淘汰 三类占比 |
| ② 强度分布直方图 | 有多少记忆在待淘汰区（<0.15，红色区） |
| ③ 冲突消解关系 | 谁取代了谁（新 → 取代 → 旧） |
| ④ 召回热度 Top15 | 哪些记忆被用得最多（用进废退的证据） |

面板同时导出 `memory_snapshot.json`，可喂给别的工具做进一步分析。

**一个意外收获**：演示脚本里我构造的假数据（10-27 写入的旧结论），
被知识库里**真实存在的**一条更晚写入的结论正确取代了——说明冲突判向能**跨来源**工作，
不只是演示数据自说自话。这个现象是跑面板时才发现的，说明可观测性确实能暴露意料之外的行为。

## 可选语义嵌入 —— 词法的边界在哪

词法双通道（TF-IDF）够快、零依赖，但有硬伤：**抓不到同义改写**。
用户问「东西下到一半就不动了」，库里写的是「流式下载挂死」——词面上几乎没重叠，词法就漏了。

本项目提供**可选**语义嵌入，但默认关闭，且**任何一步失败都自动降级回词法**，绝不让可选功能
变成跑不起来。

### 关键取舍：用 ONNX 绕开 PyTorch

常规语义方案要装 `sentence-transformers` + PyTorch（几个 GB）。本项目只用
**onnxruntime + tokenizers**（几十 MB），直接跑 ONNX 模型：

```bash
pip install onnxruntime tokenizers     # 可选依赖
python -m memory.semantic --download   # 拉取中文模型（约 95MB，一次即可）

# 用语义后端（检索层一个参数切换）
python -c "from memory.retrieval import HybridRetriever; \
           r = HybridRetriever(store, backend='semantic').build()"
```

`backend` 三档：`lexical`（默认）/ `semantic` / `hybrid`（词法+语义融合）。
模型缺失、依赖没装、加载报错——**一律降级 lexical 并记录原因，检索照常返回**。

### 实测：零词面重叠下，语义是词法的 4 倍

公平测试必须让查询和答案**一个字都不重合**，否则词法天然占便宜（它就是在匹配字面）。
评测做法：12 组「查询 ↔ 语义相关但零共同实词」的用例 + 12 条无关干扰项，**探针单独成库**
（混进 318 条真实记忆里测，真实记忆会抢占 top-k，测出来的是「在噪声里找一条」而非纯语义能力）。

| 通道 | 零词面重叠命中率（12 例） |
|---|---|
| lexical（词法） | 0.167 |
| semantic（语义） | **0.667** |
| hybrid（融合） | 0.583 |

词法基本失明（0.167），语义补到 0.667——**这是语义嵌入真正的价值场景**。

### 踩过的坑：英文嵌入模型不能拿来跑中文

第一版我用了最常见的 `all-MiniLM-L6-v2`，结果**语义比词法还差**（同义改写场景 0.0 vs 0.30）。
量了一下原因：

| 模型 | 同义句对均值 | 无关句对均值 | gap |
|---|---|---|---|
| all-MiniLM-L6-v2（英文） | 0.554 | 0.476 | **0.078** ← 几乎分不开 |
| bge-small-zh-v1.5（中文） | 0.438 | 0.251 | **0.187** ← 2.4 倍 |

英文模型在中文上「同义」和「无关」的相似度几乎重叠（gap 0.078，个别无关对 0.476 还高过同义对
0.216），排序完全乱掉。换成中文模型后 gap 拉开到 0.187 才真正可用。
**这个坑的价值在于：它不是「选错了库」，而是「选错了模型语言」——一个不测就发现不了的问题。**

## 架构

```
memory/
  embed.py          零依赖向量化：词 TF-IDF + 字 2-gram 双通道（默认）
  semantic.py       ★ 可选语义嵌入：ONNX 跑 BGE-small-zh，失败自动降级
  store.py          SQLite 存储：强度/访问/时间字段 + 状态 + 记忆关系表
  decay.py          ★ 遗忘衰减 + 使用强化
  retrieval.py      混合检索：min-max 归一化后融合「相关度 × 强度」，只召回 active 记忆
  conflict.py       ★ 冲突消解：检测 / 判向 / 消解（自动 + 待裁决两档）
  dashboard.py      ★ 可观测性：导出快照 + 渲染自包含 HTML 面板（纯 SVG）
  ingest.py         把 md 知识库抽成记忆单元（通用，含模板句清洗）
  eval.py           记忆生命周期评测（召回率 / 权重扫描 / 新旧竞争）
  conflict_eval.py  冲突消解评测（污染消除 / 误伤率）
  semantic_eval.py  词法 vs 语义评测（零词面重叠 / 模型边界 / 回归）
demo.py             端到端演示（生命周期）
conflict_demo.py    冲突消解演示（新认知推翻旧认知）
dashboard_demo.py   全流程演示 + 生成可观测性面板
tests.py            单元测试（9 个，纯内存，不依赖任何数据源）
```

CI（GitHub Actions）只装 `numpy` + `jieba` 跑测试与三个 demo——**不装 onnxruntime**，
顺便验证「默认零重依赖 + 语义缺失自动降级」这条承诺在干净环境里成立。

### 四个设计取舍 + 三个踩过的真坑（面试会被追问）

**设计取舍：**

1. **为什么默认用词法而不是语义嵌入？** 为了让任何人都能离线复现同一组数字。
   语义是**可选后端**（`backend='semantic'`），靠 ONNX 跑、失败自动降级。
2. **为什么相关度和强度要先归一化？** TF-IDF 短文本相关度落在 `[0, 0.3]`，强度在 `[0, 1]`，
   直接线性混合会让强度一项压倒相关度，权重还没调就失衡。min-max 归一化后
   `strength_weight` 才是一个真正的、单调可调的旋钮（见实验一b）。
3. **为什么记忆单元用「文件/块」而不是「句子」？** 这类笔记每条是一个自足的「坑→改法」
   原子结构，本身就是合适的召回粒度；切太碎会丢上下文，切太大检索不准。
4. **为什么消解要分「自动」和「待裁决」两档？** 见上文「误判比漏判危险」。

**踩过的真坑（都是调试中真实发现并修掉的）：**

1. **TF-IDF 相似度是语料相关的。** 同一个真冲突对，在 3 条小库算 0.26，在 318 条库能到 0.68。
   硬编绝对阈值必然错。改用**语料无关的复合信号**（词重叠 0.5 + 字重叠 0.3 + 标题命中 0.2）
   `+ 按分布自校准的阈值`。
2. **O(n²) 里重复分词会卡死。** 318 条库两两配对约 5 万次，每次重新 jieba 分词，
   程序直接挂住。改成**配对循环外预计算一次**分词结果，2.8 秒跑完。
3. **评测有副作用。** `memory.eval` 的「做旧」步骤直接改写了原库时间戳，导致后续
   冲突评测在被动过手脚的数据上得出「335 条误取代」的假结论。改成**在数据库副本上评测**。
4. **英文嵌入模型不能跑中文。** all-MiniLM-L6-v2 在中文上同义/无关几乎分不开（gap 0.078），
   语义召回 0.0 还不如词法。换中文 bge-small-zh 后 gap 0.187 才可用。
5. **评测基准会偏袒某一方。** 用「含关键词」定义 gold 时，词法天然占便宜——它就在匹配字面。
   必须专门构造**零词面重叠**用例，才测得准语义能力（见「可选语义嵌入」章节）。

> 第 3、5 两个坑最值得讲：它们暴露的都是**方法论问题**——评测不该改变被测对象的状态、
> 评测基准不该偏袒某个方案。能发现并说清这类问题，比写出功能本身更能证明工程素养。

## 局限（诚实标注）

- gold 集由关键词命中**自动生成**，属弱标注；真实评测需人工标注金标准。
- 词法检索对同义改写不鲁棒（「卡住」≈「挂死」靠字通道兜一部分）；
  语义后端可缓解，但默认不开启（为了零依赖），且中文模型仍非最优。
- 遗忘曲线参数（半衰期、增益）用的是直觉默认值，未做数据驱动调参。
- 冲突「判向」只用了「晚的优先」这一条规则，未接入来源可信度加权；
  待裁决的冲突目前只产出候选，没有实现批量裁决界面。
- 未实现记忆**压缩归档**（decay.py 已留 `consolidation_candidates` 接口）。
- 语义嵌入的中文模型（bge-small-zh）仍不如更大模型，且未做量化/加速。

## 面试怎么讲（3 分钟版）

> 我做过一个 Agent 长期记忆系统。起因是我发现**普通 RAG 假设所有文档永远有效**，
> 但真实的长期 Agent 里，库里会堆大量过时记忆，跟新记忆冲突、把上下文撑爆。
>
> 我做了三层。第一层是**强度**，`strength = 衰减 × 强化`：衰减是艾宾浩斯遗忘曲线，
> 久不用就淡出；强化是召回时抬升稳定度，而且有间距效应。检索时用相关度 × 强度排序，
> 过时记忆自动沉底。
>
> 第二层是**冲突消解**。光靠时间衰减不够——新记忆刚写进来、旧记忆还很新鲜的时候，
> 两条矛盾记忆会同时被召回，模型拿着两个相反结论瞎猜。所以我加了冲突检测：判断两条
> 记忆是否同主题，是同主题且新的晚写入，就把旧的标记为「已取代」，检索不再返回它。
>
> 我拿自己的知识库做了 **318 条真实记忆**的评测。三个结果我印象最深：
> 一，同主题新旧两条记忆时，**纯 RAG 的 top-1 命中新版只有 67%，我的记忆层是 100%**；
> 二，冲突消解把「矛盾记忆同时被召回」的比例**从 100% 降到 0%，同时在真实库上误伤为 0**；
> 三，在**零词面重叠**（查询和答案一个字都不重合）的场景下，
> **词法检索命中率 0.167，语义后端 0.667**，差了 4 倍。
>
> 最后一点我最看重：消解会**隐藏**记忆，判错就是静默丢掉一条正确记忆，比不消解更糟。
> 所以我把策略做成两档——证据强才自动取代，证据不足的只标记、交人裁决。真实库里
> 自动取代 0 对、待裁决 378 对，这才是我想要的安全边界。
>
> 技术上有两个细节值得说。一是我做了可选语义嵌入，但用 ONNX Runtime 绕开了 PyTorch，
> 装几十 MB 就能跑；而且模型缺失时自动降级回词法，绝不崩。二是我第一版用了英文嵌入
> 模型跑中文，结果语义比词法还差——量了一下，它给「同义」和「无关」的打分只差 0.078，
> 基本分不开；换成中文模型后差到 0.187 才可用。

**这段讲法为什么有效**：它展示的不是「我会用框架」，而是
① 发现 RAG 的隐含假设缺陷；② 用遗忘/强化/冲突消解这套有理论依据的机制解决它；
③ 用真实数据量化验证；④ **主动说出「误判比漏判危险」「英文模型跑不了中文」这类
自己方案的边界**。第 ④ 点最值钱——它证明你想到的不只是「怎么让它工作」，还有
「它会在哪里出错、出错了谁承担」。**这是实习岗里最稀缺的信号：工程判断力，而不是编码量。**
